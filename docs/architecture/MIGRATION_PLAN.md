# QUBIVEX: Migration Plan

Status: **The single QUBIVEX roadmap.** Phases 1–4 are done. On 2026-11-03 the
Engineering Improvement Plan (EIP) was folded in here rather than run as a second
roadmap (`docs/engineering/ARCHITECTURE_DECISIONS.md` §3); the changes are in §3a.
§2 describes the original Intel machine; development has since moved to an Apple M3 Pro
(see `IMPLEMENTATION_STATUS.md`, "Environment change").

This plan converts Colibri's *mechanisms* into a Rust runtime. It is a redesign, not a
line-by-line port. It follows the specification's phase order with two adjustments,
each marked **[ADJUSTMENT]**.

---

## 1. First reference model: OLMoE-1B-7B-0125-Instruct

### Recommendation
**`allenai/OLMoE-1B-7B-0125-Instruct`** as the first MoE reference model, with a
**tiny Qwen3-MoE fixture** as the second architecture. The fixture proves that a new
model loads through a manifest with no runtime code change.

### Why OLMoE

| Criterion | OLMoE |
|---|---|
| Licence and openness | Apache-2.0. Weights, code, data and logs are all open |
| Size | 6.9B total, about 1.3B active per token. Small enough to iterate on a laptop |
| Structure | 16 layers, hidden 2048, 64 routed experts, top-8, expert FFN 1024 (SwiGLU), no shared experts, softmax router without top-K renormalisation, MHA with QK-norm, RoPE, RMSNorm |
| Reference implementation | `transformers` `OlmoeForCausalLM`, the canonical numerical oracle |
| Colibri baseline exists | `c/olmoe.c` (the smallest, most self-contained engine), `ref_olmoe_real.json` greedy token ids, tiny-fixture tests, published numbers: 22–23 tok/s CPU (8-core Zen 4, int8), 47.4 tok/s CPU / 354.6 CUDA / 299.4 Vulkan (i5-13500 + RTX PRO 4000, Q4_K_M GGUF) |
| Formats | Official SafeTensors (bf16) and widely published GGUF (Q4_K_M ≈ 4.2 GB, Q8_0 ≈ 7.3 GB) |
| Streaming exercise | 1,024 experts × 6.3 MB (int8) ≈ 6.4 GB of routed weights against well under 1 GB dense. Capping the expert budget forces real disk streaming on any machine |

### Known limitations of the choice (and how they are covered)
- **No hot-expert structure** (Colibri #864: a near-flat usage curve). Learned pinning
  will show little gain on OLMoE. That is honest data, not a failure. The learned
  cache's value is shown later on a model with skewed routing.
- **MHA, not GQA; no shared experts; softmax routing.** These are covered by the
  **tiny Qwen3-MoE fixture** (GQA, 128 experts, top-K renormalisation), generated by
  `transformers` with pinned versions. If it loads through `transformer_moe` by
  manifest alone, the extensibility criterion is met.
- **Too small to need streaming on big machines.** Streaming is forced through the
  budget (`--ram-budget`). The planner must also produce such plans for real
  low-memory machines.

### Alternatives considered
- **Qwen3-30B-A3B / Qwen3.6-35B-A3B.** Better hot-expert structure and GQA. But the
  checkpoints are 18–23 GB+ (they do not fit this dev machine's free disk) and use
  hybrid DeltaNet layers in Qwen3.6. Recommended as the **second real model**.
- **Mixtral-8x7B.** Only 8 experts and a large dense path. A poor stress test for
  expert streaming.
- **DeepSeek-V2-Lite.** MLA attention and a shared expert. Too many new components at
  once for a first target.

## 2. Development environment constraints (observed)

| Item | Value | Consequence |
|---|---|---|
| Dev machine | Intel i7-9750H (6C/12T, AVX2, **no AVX-512**), 16 GB RAM, macOS x86-64 | AVX2 is the first SIMD target. NEON and AVX-512 are written against CI |
| Free disk | **8.6 GB** (99% full) | The bf16 OLMoE checkpoint (about 14 GB) **does not fit**. Q4_K_M GGUF (about 4.2 GB) fits. See blocker B1 |
| GPU | No CUDA | CUDA work (Phase 8) needs a Linux and NVIDIA machine or a CI runner |
| Rust | 1.91.0 stable | MSRV proposed: 1.85 (edition 2024) |

## 3. Phase plan with milestones and exit criteria

Every phase ends with `cargo fmt --check`, `cargo clippy --workspace --all-targets
-D warnings` and `cargo test --workspace` green in CI, `IMPLEMENTATION_STATUS.md`
updated, and the relevant ADRs moved to Accepted.

### Phase 1: Rust foundation (about 1 week)
Workspace, `qubivex-core` (ids, `DType`, `Shape`, error enums, config types),
`apps/cli` skeleton with `qubivex --version`, and CI on Linux x86-64 and macOS
(fmt, clippy, test, `cargo deny`). Also the architecture dependency-rule test and the
model-name grep guard. Workspace lints and dependency inheritance per ADR-001 and
`docs/development/RUST_GUIDELINES.md`, plus an MSRV job. The CI job slots for `miri`
(pinned nightly) and `loom` (`RUSTFLAGS="--cfg loom"`) are added in the phase that
first adds unsafe or concurrent code (Phase 4), not as empty jobs now.
**Spike, timeboxed to 3 days:** tensor-engine benchmark for ADR-002, on OLMoE expert
shapes (2048×1024 and 1024×2048) at S=1 and S=128. Candidates are Candle (f32, bf16,
q8_0, q4_k), own AVX2 int8 row-scaled GEMV, and own ggml-block Q4_K GEMV. Metrics are
ns per expert FFN, GB/s and exactness against an f64 reference.
**Exit:** clean workspace and a recorded ADR-002 decision.

### Phase 2: Hardware detection
`qubivex-hardware`: CPU (SIMD set, P/E cores, NUMA), RAM (MemAvailable, cgroup v1/v2,
macOS `vm_stat`), GPUs (a child-process probe with timeout for NVML/CUDA driver and
Vulkan; "unavailable: reason" otherwise), and storage (mounts, fs type, capacity).
Add an optional `qubivex doctor --storage` read benchmark (sequential, random 4 MB,
O_DIRECT/F_NOCACHE delta).
**Exit:** `qubivex system [--json]` shows the real profile on Linux and macOS, and
unit tests run on recorded `/proc` and `sysctl` fixtures.

### Phase 3: Model metadata and registry
Manifest schema v1 (JSON Schema published in `docs/model-support/`), SafeTensors and
GGUF header readers, `TensorIndex`, `ArchitectureRegistry`, the `transformer_moe`
factory's `parse_config` and `tensor_schema`, cross-validation (manifest against
config.json against headers; exact byte sizes; optional sha256), and discovery over
model directories. Tiny fixtures are generated by pinned `transformers` scripts:
OLMoE-tiny and Qwen3-MoE-tiny.
**Exit:** `qubivex models list` and `qubivex models inspect <id>` work for both tiny
fixtures and the real OLMoE GGUF. A tampered header is rejected with a useful error.
Neither code path contains a model name.

### Phase 4: CPU inference prototype **[ADJUSTMENT]**
The specification puts expert streaming at Phase 6. Here, **a minimal
`ExpertStore` (all-resident and LRU-on-disk, synchronous demand loads, leases,
in-flight dedup) is built in Phase 4**, and the MoE layer fetches experts *only*
through it from day one. That way the central claim, correctness at any cache size,
is tested from the first token, and there is never a direct weight path to remove
later.
Components: tokenizer (HF `tokenizers` and chat template), embeddings, RMSNorm, RoPE,
attention (MHA and GQA, QK-norm), router (softmax or sigmoid, top-K, optional
renormalisation), SwiGLU expert, **expert-major prefill batching with rank-order
combination**, output head, greedy and temperature/top-p sampling, and a simple f32
KV cache.
Numerical tests:
- tiny fixtures: per-layer router logits, selected ids, routing weights, attention
  output, expert output and final logits against `transformers` (f32, tolerance about
  1e-5 relative), and greedy tokens equal;
- **cache-capacity sweep** {1, 2, small, medium, all}: identical tokens *and bitwise
  identical logits* across capacities (invariant 1);
- real OLMoE: greedy tokens for Colibri's `ref_olmoe_real.json` prompt.
**Exit:** `qubivex run --model <olmoe> --prompt …` generates correct text on CPU, and
every numerical test passes.

### Phase 5: Memory planner
Budgets (RAM and VRAM separate), tensor-role-driven placement, KV accounting with KV
and expert-cache room sharing (Colibri `kv_room_fit` semantics), non-uniform
per-layer cache budgets, profiles (performance, balanced, saver, custom), a pressure
monitor (stop prefetch, then shrink cache, then refuse admission; never kill an
active request), and `MemoryLedger`.
**Exit:** `qubivex plan <model> [--ram-budget] [--ctx]` explains the placement with
reasons. Property tests cover plans that never exceed budget for random hardware and
models. A ledger-against-RSS test runs on real OLMoE.
**Progress (2026-11-03):** slice 1 is done: `qubivex-memory` (footprint from roles,
profiles, the shared KV/expert room with admission, per-layer slots, `MemoryLedger`),
`qubivex plan`, and property tests (ADR-005 amendment 1). Slice 2 is done: the engine
plans at load, the KV takes room back from the expert store as it grows, the ledger
is charged, and the ledger-against-RSS test passes on the real model (amendment 2).
Slice 3 is done: the pressure monitor, with an opt-in external RAM-hog test on the
real model (amendment 3). **Phase 5 is complete;** every exit check passes.

### Phase 6: Expert streaming (full)
Bounded priority I/O queue, a pool of I/O workers, `acquire_many` that issues all of
a layer's misses before waiting, slab reuse, adjacent-extent coalescing, a direct-I/O
option (`O_DIRECT` / `F_NOCACHE`) and an io_uring option (Linux, feature-gated), both
**default off until measured**, ported LFRU and hysteresis policies, multi-drive
mirrors, and metrics.
**Exit:** OLMoE runs correctly with an expert budget well below its expert size (for
example 1 GB of 6.4 GB). Duplicate-request and cancellation stress tests pass. The
benchmark records the hit rate, bytes read per token and tok/s.
**Progress (2026-11-03):** slice 1 is done: per-layer pools with slab reuse and LFRU
(the default) in the store, the engine sizing pools with the plan's `distribute`,
`qubivex bench --routing-trace` and the trace-replay example, and the hit rate, bytes
per token and slab allocations in the bench record (ADR-008 amendment 1). At a 1 GiB
budget the hit rate goes from 0% to 10.9% and decode from 12.0 to 14.9 tok/s. Next:
the I/O queue, worker pool and `acquire_many`.
Slice 2 is done: `acquire_many` and the `Batch` iterator; the MoE layer requests a
whole layer through `with_experts`; a priority queue with 4 I/O threads by default;
cancellation and error delivery; and within-expert coalescing (ADR-006 amendment 1).
At 1 GiB, decode goes from 14.9 to 20.2 tok/s with identical tokens.
Slice 3 is done: direct I/O (`--direct-io`: `F_NOCACHE` on macOS, aligned `O_DIRECT` on
Linux), off by default; the warm I/O matrix (buffered against direct at 0–8 I/O threads);
and the exit check: at a 1 GiB budget (149 MiB of slots for 3.63 GiB of experts), 160
tokens match the all-resident run at 19.9 tok/s, with a 10.4% hit rate and 427 MiB read
per token (ADR-006 amendment 2). **Phase 6 is complete.** Moved out: io_uring and the
cold `O_DIRECT` rows (they need a Linux host), multi-drive mirrors and per-device queues.

### Phase 7: Predictive loading
Router-lookahead predictor (next layer's norm and router on the current hidden state,
EMA momentum, confidence cutoff, width cap), prefetch at `Prefetch` priority, the
eviction guard, cancellation at layer and turn boundaries, and metrics (recall, useful
prefetch rate, wasted bytes, lead time, blocking time saved).
**Exit:** a measured reduction in blocking expert-load time on a cache-constrained
OLMoE benchmark, with negative results recorded if it does not help. A test proves
that routing is identical with prediction on and off.
Slice 1 is done (ADR-008 amendment 2): the lookahead predictor (EMA, confidence
cutoff, width cap), `ExpertStore::prefetch` at `Prefetch` priority with the LFRU guard,
a prediction that never evicts its own experts, promotion and cancellation of queued
prefetches at layer and turn boundaries, a pressure stop, and the metrics (recall,
precision, ready/late, wasted bytes, lead time, blocked time). **Exit met:** at 1 GiB,
blocked time falls from 8.29 to 4.87 ms per token (guard on) or 3.95 ms (guard off),
and decode goes from 19.87 to 20.3–20.5 tok/s. At 2–3 GiB and all resident there is no
gain (guard on) or a 1–2% loss (guard off), so prefetch stays opt-in (`--prefetch`).
The routing-identity test passes on every fixture. Not built: a disk-saturation
throttle, lookahead beyond one layer, and next-token layer-0 prediction.

### Phase 8: GPU acceleration
**Order amended 2026-11-03 (ADR-007): Metal first** (`qubivex-backend-metal`, testable on
the M3 Pro), then CUDA, then Vulkan. The CUDA work below is unchanged, but comes second.
Metal slices: (1) kernels with bit-identical CPU parity and benches (**done 2026-11-03**,
ADR-011); (2) command-buffer batching, zero-copy weights, plan-time placement and token
parity in the engine (**done 2026-11-03**, ADR-011 amendment 1: bit-identical tokens, but
no decode gain, because a lone submission costs about 110 µs and the GPU idles between
tokens; the CPU stays the default); (3) keeping the GPU busy (one submission per layer or
token, with norms, RoPE, attention and the expert FFN as bit-exact Metal kernels), faster
bit-exact kernels and the Metal exit benchmark (**done 2026-11-03**, ADR-011 amendment 2:
portable CPU numerics, whole layers on Metal with experts wrapped in place; decode
26.4 → 44.5 tok/s and prefill 33 → 77 tok/s with experts resident, bit-identical; slower
than the CPU when the pools hold fewer experts than top-k); (4) small expert caches
(**done 2026-11-03**, ADR-011 amendment 3: asynchronous submission built; overlapping
streamed experts with GPU work measured slower than the CPU pass, so the plan runs the
CPU pass when a pool is smaller than top-k); (5) routing on the GPU (one submission per
token) and a concurrent encoder.
CUDA (`cudarc` and ported kernels): device buffers, ledger accounting, dense
layers on the device, a VRAM expert tier, hybrid split (`hybrid_split.h`), and CPU/GPU
in-frame combination in rank order. Then Vulkan (`ash` and ported shaders). Parity
tests against CPU tokens use a documented drift tolerance (as Colibri's
`gpu-parity.md` does).
**Exit:** hybrid inference with correct VRAM accounting, benchmarked against Colibri
CUDA OLMoE on the same machine.

### Phase 9: API and serving
Axum gateway: `/health`, `/v1/models`, `/v1/chat/completions` and `/v1/completions`
(SSE), `/v1/system*`, model load and unload (admin token), `/metrics`. Admission
control from the planner's KV accounting, cancellation, timeouts, request ids, and
structured errors with no paths leaked.
**Exit:** an OpenAI SDK client works, concurrent conversations get independent KV,
and a cancellation test passes.

### Phases 10–11
As in the specification: batched expert execution across requests, KV prefix reuse,
paged KV, NUMA, multi-device; then a CLI UX catalogue and recommendations UI.

### 3a. Folded in from the Engineering Improvement Plan (2026-11-03)
- **Phase 4.5: tensor descriptors (done, ADR-009).** `TensorDesc` (byte strides, offset,
  zero-copy views) in `qubivex-core`; typed `TensorView`, `TensorViewMut` and `Tensor<T>`
  in `qubivex-compute`. The runtime's dense weights use `Tensor<u8>`. Decode output is
  byte-identical, with no speed regression.
- **In-workspace benchmarks (done).** Criterion benches for the existing kernels
  (`qubivex-backend-cpu/benches/kernels.rs`, including a DRAM-bound decode group) and
  `qubivex bench`, a decode/prefill harness that records the EIP §13.3 fields (hardware,
  flags, threads, warm-up, median and P95, peak memory, and a token check as the error
  field). Protocol and the 2026-11-03 baseline: `docs/performance/BENCHMARKING.md`.
  Every later kernel change is measured before and after against these.
- **Phase 4 follow-ups, each measured:** AVX2 kernels; the dequantise + `gemm` prefill
  and the spinning pool that ADR-002 accepted but which are not built yet; a faster
  lossless Q4_K kernel (the EIP's quantised GEMV target is ≥ 70% of STREAM; the
  baseline measures Q4_K at 17 GiB/s, about 22% of the 80 GiB/s bf16 streams from DRAM
  on the M3 Pro, and the kernel is limited by compute, not memory).
- **KV cache on `Tensor<f32>`** with `narrow` views: the next consumer of ADR-009, with
  its own benchmark.
- **Extensibility:** a dense (non-MoE) architecture and a real SafeTensors run, alongside
  the existing MoE path.
- **Precision (ADR-010):** lossless by default; lossy behaviour only as named opt-ins,
  never in a profile.
- **Graph IR and compiler: deferred** until operator contracts exist and a second
  architecture family or the first GPU backend shows a need (future ADR-012).
- The EIP's `qubivex-tensor` and `qubivex-quant` crates are not created. Their content
  lives in `qubivex-core`, `qubivex-compute` and `backend-cpu::formats`.

### Additions from the improvement evaluation (Addendum §4)
[IMPROVEMENTS_EVALUATION.md](IMPROVEMENTS_EVALUATION.md) maps each addendum item to
Colibri evidence, a verdict and a phase. It changes the phases above as follows:
- **Phase 3:** typed failure paths, plus the start of a fault-injection `ExpertSource`
  wrapper (EIO, short reads, corrupt bytes).
- **Phase 5:** an admission-logic unit test (projected KV must not push the expert
  cache below the floor), and an external RAM-hog pressure test.
- **Phase 6:** the I/O strategy benchmark matrix (mmap, pread pool, io_uring,
  O_DIRECT/`F_NOCACHE`) per OS and device; per-device queues; `doctor --storage` on
  every OS; a Rust trace-replay simulator for cache policies.
- **Phase 7:** prefetch priority below demand, stale-speculation cancellation, and a
  throttle when the disk is saturated.
- **Phase 9:** memory-aware admission, fair prefill chunking, per-request failure
  isolation, and the runtime bottleneck diagnoser.
- **Phase 11:** `models recommend` runs the real planner over manifests.

## 4. Benchmarking against Colibri

Build Colibri's `olmoe` engine at the pinned commit `0a5504a1` and run both engines on
the same machine, model (Q4_K_M GGUF, which both read directly), prompt, context,
generation length, thread count and cache state (cold means page cache dropped; warm
means second run). Record tok/s for prompt and decode, time to first token, expert hit
rate, bytes read per token and peak RSS, following Colibri's
`docs/benchmarking.md`. Building and running Colibri executes third-party code. That
step will be confirmed with you when we reach it.

## 5. Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Rust CPU kernels slower than Colibri's hand-tuned C SIMD | High | High | Phase 1 spike; port hot kernels with `std::arch`; Criterion regressions in CI; accept selective FFI to C kernels if needed (ADR-002 allows it) |
| R2 | Bit-exact invariant broken by parallel reductions | Medium | High | Fixed reduction order per kernel; capacity-sweep test compares logits bitwise on the same kernel set |
| R3 | `unsafe` spread (slabs, mmap, SIMD, FFI) | Medium | High | Workspace `unsafe_code = "deny"` with per-crate opt-in for 3 crate kinds only; `undocumented_unsafe_blocks` denied; scalar twins of SIMD kernels so Miri can run; ASan job |
| R11 | Races in leases, in-flight dedup or eviction (Colibri hit several) | Medium | High | `loom` model tests of the slot state machine under `cfg(loom)`; documented atomic orderings |
| R12 | Integer overflow or truncation on untrusted header sizes | Medium | High | Checked arithmetic and `TryFrom` for all input-derived sizes; `cast_possible_truncation` lint; fuzz the header parsers (`cargo fuzz`) in Phase 3 |
| R4 | Scope creep toward Colibri's feature set | High | Medium | Non-goals list; Colibri-only features listed explicitly as out of scope (analysis §14) |
| R5 | Async misuse (blocking Tokio, unbounded queues) | Medium | Medium | Sync hot path with dedicated threads (design §4.5); bounded channels only; clippy lint for `unbounded_channel` |
| R6 | Disk I/O behaviour differs per OS and drive | High | Medium | All I/O modes measured per machine; defaults chosen from measurements; `doctor --storage` |
| R7 | GPU backend effort (CUDA, Vulkan, Metal) | High | High | Defer until CPU is correct; port Colibri kernels and shaders (Apache-2.0) rather than writing new ones |
| R8 | OLMoE has no hot experts, so cache learning cannot be demonstrated | Certain | Low | Second real model with skewed routing (Qwen3-30B-A3B) when disk allows |
| R9 | Planner budgets diverge from real RSS | Medium | High | `MemoryLedger` + RSS reconciliation test; refuse admission instead of OOM |
| R10 | Licence and attribution when porting | Low | Medium | `NOTICE` and `THIRD_PARTY_NOTICES.md` entries with Colibri commit per ported file |

## 6. Blockers needing your decision

- **B1. Disk space.** 8.6 GB free cannot hold the bf16 OLMoE checkpoint (about
  14 GB), which the full-precision numerical oracle needs. Options: free about 25 GB,
  use an external or second drive (which also tests multi-storage), or validate the
  real model only through the Q4_K_M GGUF (about 4.2 GB) and greedy-token agreement
  with Colibri, keeping full-precision oracles to tiny fixtures.
- **B2. CUDA hardware** for Phase 8: a Linux NVIDIA machine or a GPU CI runner.
- **B3. Repository and remote.** `qubivex/` is not a git repository yet. Phase 1
  starts with `git init`; tell me if there is a remote to use.
